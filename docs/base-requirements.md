OptiSigns DevOps Engineer Technical Assessment
AI-Assisted Video Upload Platform on Local Kubernetes
1. Goal
Your task is to build and deploy a small but real video upload and processing platform on a local Kubernetes environment.
The platform must include:
A ReactJS frontend that allows users to upload video files.
A NestJS GraphQL backend that handles upload, file listing, and processing status.
Support for uploading MP4 video files, including 4K input.
Video processing that generates multiple video versions and a thumbnail.
Temporary file storage backed by NFS or an NFS-compatible shared filesystem.
Deployment on local Kubernetes.
High availability and failover considerations at the pod/workload level.
Clear documentation showing how the system is built, deployed, tested, and cleaned up.
The final result should be a working system, not just configuration files.
2. Tooling and Resource Policy
There is no strict limitation on the tools, services, AI assistants, plugins, libraries, automation methods, or frameworks you may use.
You are free to use any resources you believe are necessary to deliver a complete, working, production-minded solution.
This may include, but is not limited to:
AI tools: ChatGPT, Claude, Gemini, Cursor, GitHub Copilot, Claude Code, or similar tools.
DevOps tools: Terraform, Helm, Kustomize, Skaffold, Argo CD, GitHub Actions, GitLab CI, Docker, Trivy, Snyk, or equivalent tools.
Kubernetes tools: kind, k3d, minikube, Docker Desktop Kubernetes, or any equivalent local Kubernetes environment.
Observability tools: Prometheus, Grafana, Loki, OpenTelemetry, or equivalent tools.
Development libraries, SDKs, open-source packages, plugins, and automation scripts.
Cloud services, if you choose to include an optional cloud deployment.
However, you must clearly document:
What tools and services you used.
Why you chose them.
What problem each tool or service solves.
What was generated by AI or external tools.
What you manually reviewed, modified, or verified.
What trade-offs or limitations your solution has.
How to reproduce, test, and clean up your deployment.
Using many tools is not automatically better.
We evaluate your engineering judgment, not the number of tools used.
Blindly using tools, AI-generated output, or generated infrastructure without understanding, verification, or documentation will be evaluated negatively.

4. Application Requirements
4.1 Frontend
Build or provide a ReactJS frontend that allows users to:
Select an MP4 video file from their local machine.
Upload the video file to the backend.
See whether the upload succeeded or failed.
See the processing status of uploaded videos.
List uploaded videos.
View the generated thumbnail.
Access the generated video versions.
The frontend should communicate with the backend through GraphQL.
4.2 Backend
Build or provide a NestJS GraphQL backend.
The backend must provide APIs for:
Uploading a video file.
Listing uploaded videos.
Returning processing status.
Returning metadata for generated video versions and thumbnails.
Health checking.
The /uploads directory, or equivalent upload storage path, must be backed by NFS or an NFS-compatible shared filesystem.
4.3 Video Processing
The system must support uploading MP4 video files, including 4K input.
After upload, the system must process the video and generate:
2K version.
1080p version.
720p version.
480p version.
Thumbnail image.
The frontend must display the uploaded video, processing status, thumbnail, and available processed video versions.
For this assessment, you may demonstrate the workflow using one short sample video.
You must explain how your design would need to change for larger production workloads, high concurrency, long videos, or heavy transcoding traffic.

Frontend deployment.
Backend deployment.
Video processing component deployment.
NFS-backed or NFS-compatible shared storage.

6. Storage Requirement
Temporary file storage must be backed by NFS or an NFS-compatible shared filesystem.
The storage must be shared across backend pods and video processing components.
You must demonstrate that uploaded files and processed outputs remain available after backend pod restart or failover.
You may choose any implementation approach, but you must explain:
Why you chose it.
How it works.
How it behaves during pod failover.
What its reliability limitations are.
What would need to change for production.
7. High Availability and Failover Requirements
You must demonstrate at least:
Backend pod restart or failover.
Frontend pod restart or failover.
Uploaded files remain available after backend pod restart.
Processed video outputs remain available after backend pod restart.
Video processing can recover, retry, or be handled safely after processing component failure.
Rolling update or rollback behavior.
You must include evidence showing how you tested these cases.

12. Evaluation Criteria
We will evaluate:
Whether the system works end to end.
Whether the local deployment is reproducible.
Whether video upload and processing work correctly.
Whether storage is shared and survives pod restart/failover.
Whether Kubernetes resources are designed with production awareness.
Whether failover behavior is demonstrated clearly.
Whether documentation is clear and honest.
Whether AI was used responsibly and verified properly.
Whether trade-offs and limitations are understood.
Whether the solution would be maintainable by an engineering team.
We do not expect a perfect production system.
We do expect a working system, clear reasoning, practical engineering judgment, and evidence that you can solve real infrastructure and application deployment problems.
